## 2. Les 8 chantiers de la Phase 5 — Fiabilisation & Industrialisation

Classés par ratio impact/effort. Les 4 premiers sont des correctifs, les 4 suivants des leviers.

### 5.1 ⚠️ CRITIQUE — Sortir la base SQLite de `/tmp`
`DB_PATH = /tmp/ai_maths_data/attempts.db` : **toutes les données de campagne disparaissent
au reboot**. Déplacer vers `data/attempts.db` dans le repo (gitignoré) + backup automatique.
C'est la matière première du projet ; la perdre = refaire toutes les campagnes.

### 5.2 Timeout sur le REPL
`send_request()` fait des `readline()` bloquants sans timeout. Une tactique qui diverge
(`nlinarith` sur un but trop gros, `decide` sur un terme géant) **gèle toute la campagne**.
Le paramètre `timeout_per_attempt_sec` existe dans `ProverConfig` mais n'est jamais utilisé.
Fix : lecture avec timeout (select/thread), kill + restart du REPL en cas de blocage,
l'échec-timeout devient un diagnostic réinjecté ("tactic X timed out, try another approach").

### 5.3 Cohérence REPL ↔ Juge Prod (faux négatifs d'imports)
`check_code()` supprime tous les `import` et s'appuie sur le préchargement fixe
(`Mathlib.Tactic` + 3 modules). Une preuve nécessitant un module hors préchargement
(ex. `Mathlib.Analysis.SpecialFunctions.Log.Basic`) risque d'échouer en REPL alors
qu'elle passerait en prod → candidats valides jetés. Fix : précharger `import Mathlib`
entier dans le warmup (coût mémoire unique au démarrage, le LXC tient).
Le juge prod reste l'autorité finale — ça ne change pas.

### 5.4 Métriques propres + rapport dédupliqué
- `stats.py` mélange problèmes, sous-lemmes (`*_step1`) et doublons → "15/31 résolus" ne
  veut rien dire ; le vrai chiffre est 10/16 distincts. Séparer : campagnes benchmark
  (set figé, pass@k, problèmes distincts) vs tentatives libres.
- `bounty_report.py` : dédupliquer (mathd_algebra_478 y figure 5 fois) — garder la
  meilleure preuve par théorème. Un rapport de certification avec des doublons décrédibilise.
- Enregistrer le coût Gemini réel (actuellement $0.0000).

### 5.5 Escalade de modèles (voir §3)
Tentatives 1-2 : `deepseek-chat` (rapide, quasi gratuit). Échec → tentatives 3+ :
`deepseek-reasoner` (raisonnement profond, bien meilleur sur AMC/AIME durs).
Juge round-trip : **un modèle différent** du formaliseur (ex. Gemini) pour tuer le
biais d'auto-validation.

### 5.6 Retrieval sérieux (le levier le plus sous-exploité)
Le retrieval actuel = 3 patterns codés en dur + 2 mots-clés. Remplacer par :
- **LeanSearch** (recherche sémantique, API publique) avec l'énoncé complet,
- Loogle avec des requêtes construites depuis le **goal state** (pas l'énoncé),
- en réparation d'`unknown identifier`, requête ciblée sur l'identifiant halluciné,
- tactique `exact?`/`apply?` exécutée dans le REPL comme oracle de prémisses.

### 5.7 Parallélisme pass@k réel
La boucle actuelle est séquentielle (répare l'historique). Ajouter le tir parallèle :
k générations indépendantes à températures variées sur le même prompt, premier succès
gagne. Combiner : vague parallèle → si tout échoue, boucle de réparation sur le
meilleur candidat (celui avec le moins d'erreurs).

### 5.8 Campagne complète MiniF2F 244 + PutnamBench
Le chiffre de référence public. Puis PutnamBench (niveau supérieur) pour mesurer le
plafond réel. Chaque campagne = un tag git + un rapport figé dans `reports/`.

## 3. Stratégie modèles (DeepSeek en API)

| Usage | Modèle | Pourquoi |
| :--- | :--- | :--- |
| Tentatives 1-2 (proof direct) | `deepseek-chat` | ~$0.0001/preuve facile, latence faible ; résout déjà les mathd_* en 1 coup |
| Escalade (échecs, AMC/AIME+) | `deepseek-reasoner` | Chain-of-thought long, écart massif sur les problèmes de compétition ; coût toujours négligeable à notre échelle |
| Plan NL du Blueprint | `deepseek-reasoner` | La qualité du plan conditionne tout le reste |
| Rétro-traduction round-trip | `deepseek-chat` | Tâche de traduction simple |
| Juge d'équivalence round-trip | **Gemini** (ou autre fournisseur) | Jamais le même modèle qui formalise ET juge |

Notes d'implémentation `deepseek-reasoner` : ignorer `temperature` (non supporté en mode
raisonnement), prévoir `max_tokens` large (le raisonnement est verbeux), extraire le
contenu final hors bloc de raisonnement, timeout HTTP à 120 s et non 30 s.

Horizon suivant : les modèles **spécialisés Lean** (DeepSeek-Prover-V2, Kimina-Prover)
dominent miniF2F (>80 %) mais ne sont pas sur l'API officielle DeepSeek — poids ouverts
via hébergeurs tiers ou GPU local. À évaluer quand 5.1-5.7 seront faits : le harnais
(REPL + retrieval + blueprint) est exactement ce qu'il faut pour les exploiter.

## 5. Principes non négociables (inchangés)

1. Jamais de métrique au doigt mouillé — set figé, problèmes distincts, pass@k explicite.
2. Le REPL itère, la prod juge — aucune soumission sans `#print axioms` sur le LXC.
3. Tout est tracé, coûts compris — et la base ne vit plus dans `/tmp`.
4. L'échelle avant le sommet — miniF2F complet → PutnamBench → bounties.
5. Un énoncé mal formalisé vaut zéro — le round-trip garde un juge indépendant.
