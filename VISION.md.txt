# VISION — De la plomberie au programme de résolution de bounties

> Objectif : transformer AI-Maths-Researcher en un système capable de résoudre des problèmes
> de niveau olympiade/recherche en Lean 4, avec des métriques honnêtes à chaque étape.
> Dernière mise à jour : 2026-09-17.

---

## 1. Constat de départ

**Ce qui existe (l'échafaudage) :** infra LXC avec Mathlib précompilé, connecteur SSH,
audit anti-`sorry`, déploiement Git automatisé. Étapes 3, 6, 7, 8 du pipeline.

**Ce qui manque (le cerveau) :** la boucle de preuve IA (étape 5), la décomposition en
lemmes (étape 4), l'autoformalisation (étape 2). Aujourd'hui il n'y a **aucun appel LLM
dans le code** — l'agent, c'est un humain qui pilote un modèle à la main.

**Le principe directeur reste le bon et ne change pas :**
le LLM propose, le compilateur Lean dispose. Aucune confiance dans le texte généré,
confiance totale dans le vérificateur.

---

## 2. Architecture cible

### 2.1 La pièce maîtresse : le REPL Lean persistant

Le goulot d'étranglement actuel est le cycle de feedback : un aller-retour SSH +
`lake env lean` = 30 à 60 s par tentative. Une boucle de preuve sérieuse fait des
**centaines** de tentatives par problème. À 45 s la tentative, c'est mort.

Solution : [leanprover-community/repl](https://github.com/leanprover-community/repl)
(ou Pantograph) tournant en daemon sur le LXC, Mathlib importé **une fois** en mémoire.
Chaque tentative devient un échange JSON en ~1-3 s, avec en prime l'état des buts
(*goal state*) après chaque tactique — exactement ce qu'il faut rétro-injecter dans
le prompt.

- Le SSH direct actuel (`verifier.py`) reste le **juge final** avant tout commit :
  fichier complet, compilation propre, audit d'axiomes. Défense en profondeur.
- Le REPL est l'outil d'**itération**. Ne jamais soumettre sur la seule foi du REPL.

### 2.2 La boucle de preuve (étape 5, enfin codée)

Deux stratégies existent dans la littérature ; on commence par la moins chère :

**A. Génération de preuve entière + réparation (à faire en premier)**
```
prompt(énoncé + prémisses retrouvées + erreurs précédentes)
  → le modèle écrit la preuve complète
  → REPL compile
  → succès ? fini. échec ? erreurs + goal state réinjectés, on recommence
  → k tentatives en parallèle (pass@k), température variée
```
C'est simple, ça exploite bien les modèles frontier, et c'est l'état de l'art
"économique" (~30-50 % sur miniF2F avec un bon modèle et k modeste).

**B. Recherche arborescente au niveau tactique (plus tard, si besoin)**
Best-first search sur l'arbre des états de but, le modèle propose des tactiques
candidates à chaque nœud. Plus puissant, beaucoup plus coûteux. À n'ajouter que
quand la stratégie A plafonne et que la base de tentatives le prouve.

**Règles de la boucle :**
- Budget explicite par problème (nb de tentatives, tokens, euros). Tout est loggé.
- Rétro-injection structurée : message d'erreur + goal state + extrait de la doc
  de la tactique fautive, pas juste "ça ne compile pas".
- `sorry` autorisé **pendant** la recherche (pour valider un squelette de preuve
  lemme par lemme), interdit à la soumission.

### 2.3 Retrieval de prémisses (le multiplicateur silencieux)

La moitié des échecs LLM en Lean, c'est un nom de lemme Mathlib halluciné.
Avant chaque génération :
- interroger **loogle** (recherche par signature de type) et **LeanSearch/moogle**
  (recherche sémantique) avec l'énoncé,
- injecter les 10-20 signatures pertinentes dans le prompt,
- en réparation, si l'erreur est `unknown identifier`, relancer un retrieval ciblé.

### 2.4 Planificateur (étape 4)

Pour tout problème non trivial : le modèle produit d'abord un **plan en langage
naturel**, puis un squelette Lean où chaque étape est un lemme `:= sorry`. Le
squelette doit compiler (avec les sorry) **avant** qu'on attaque les lemmes un par
un via la boucle 2.2. C'est le workflow *blueprint* des grands projets de
formalisation (FLT, PFR de Tao), et ça transforme un problème insoluble en n
sous-problèmes attaquables.

### 2.5 Autoformalisation (étape 2) — avec garde-fou

Le danger mortel du bounty : **prouver un énoncé qui n'est pas le bon**. Validation
en trois temps :
1. l'énoncé formalisé compile (types + hypothèses),
2. **round-trip** : un second appel LLM (contexte vierge) retraduit le Lean en
   langage naturel ; un juge compare à l'énoncé d'origine,
3. test de non-vacuité : tenter de prouver la **négation** ou vérifier que les
   hypothèses ne sont pas contradictoires (sinon tout est prouvable).

## 3. Roadmap par phases — chaque phase a une métrique de sortie

### Phase 0 — Assainir les fondations (quelques jours)
- [ ] Corriger `verifier.py` : `escaped_code` calculé mais jamais utilisé, parsing
      `"error:" in combined` fragile → passer le code par stdin/scp plutôt que par
      heredoc dans une commande quotée.
- [ ] Remplacer l'audit `grep sorry|axiom` par un vrai audit `#print axioms <thm>`
      généré automatiquement pour chaque théorème de `problems/`.
- [ ] Installer le REPL Lean sur le LXC, le wrapper en daemon, écrire le client
      Python (`agent/repl_client.py`).
- **Sortie mesurable :** temps de feedback < 5 s par tentative.

### Phase 1 — La boucle de preuve minimale (1-2 semaines)
- [ ] `agent/prover.py` : boucle génère→compile→répare (stratégie A), appels API
      (modèle frontier), pass@k parallèle, budget par problème.
- [ ] Base SQLite des tentatives + un script de stats (taux de succès, itérations
      moyennes, coût par preuve).
- [ ] Retrieval loogle/LeanSearch intégré au prompt.
- **Sortie mesurable :** taux de résolution sur **50 problèmes de miniF2F-test**.
  C'est le vrai test d'intelligence des modèles. Attendu : 30-50 %. En dessous de
  20 %, c'est la boucle qui est mauvaise, pas le modèle.

### Phase 2 — Planification et décomposition (2-4 semaines)
- [ ] Mode blueprint : plan NL → squelette Lean avec `sorry` → résolution lemme
      par lemme → assemblage → juge final.
- [ ] Réattaquer les échecs de la Phase 1 avec ce mode.
- **Sortie mesurable :** gain de points sur miniF2F vs Phase 1 ; premiers problèmes
  niveau AMC12/AIME résolus de bout en bout.

### Phase 3 — Autoformalisation vérifiée (en parallèle de la Phase 2)
- [ ] Pipeline énoncé texte → Lean avec le triple garde-fou (compile, round-trip,
      non-vacuité).
- **Sortie mesurable :** sur 20 énoncés connus dont la formalisation Mathlib existe,
  ≥ 18 formalisations jugées équivalentes.

### Phase 4 — Cibles réelles, par ordre de difficulté croissante
1. **PRs Mathlib** : lemmes manquants découverts en Phase 1-2 (le retrieval qui
   échoue est un détecteur de trous dans Mathlib). Une PR acceptée = crédibilité
   réelle, atteignable en quelques mois.
2. **Bounties d'écosystème** : projets type Equational Theories — des milliers de
   petites implications à prouver, format idéal pour un système automatisé.
3. **Compétitions/benchmarks** : PutnamBench, problèmes récents d'olympiades.
4. **Bounties à gros chèque / problèmes ouverts** : seulement quand les niveaux
   1-3 sont validés par des résultats. Pas avant.

---

## 4. Principes non négociables

1. **Jamais de métrique au doigt mouillé.** Un claim de capacité = un chiffre sur
   un benchmark public reproductible.
2. **Le REPL itère, la prod juge.** Aucune soumission sans compilation complète
   fichier + audit `#print axioms` sur le LXC.
3. **Tout est tracé.** Chaque tentative en base, coût compris. C'est la matière
   première pour améliorer les prompts et choisir les modèles.
4. **L'échelle avant le sommet.** miniF2F → Mathlib PR → bounties d'écosystème →
   gros bounties. Sauter un barreau = temps perdu, pas du temps gagné.
5. **Un énoncé mal formalisé vaut zéro.** Le round-trip d'autoformalisation n'est
   pas optionnel.

---

## 5. Coûts et ordres de grandeur (à affiner avec les données de la Phase 1)

- Une preuve miniF2F facile : quelques centimes à ~1 € (pass@k modeste).
- Un problème AIME dur en mode blueprint : 1-10 € selon la profondeur.
- La base de tentatives dira vite quel modèle a le meilleur rapport
  preuves/euro — c'est un des buts explicites du projet.
